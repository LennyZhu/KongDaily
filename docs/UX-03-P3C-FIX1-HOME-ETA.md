# Phase 3C-FIX1 · 首页巴士 ETA 与铁路卡片

## 根因与证据

已复现一条会让 B2 无限 Loading 的代码路径。旧版 `requestBusJson` 的 20 秒计时器只调用 `AbortController.abort()`。如果底层请求或 `response.text()` 收到取消信号后仍保持 pending，读取就不会兑现或拒绝。此时 `useBusEta` 无法运行 `finally` 清除 Loading 和占用中的请求，之后的轮询也会被 in-flight 检查挡住。

对照 `dea60d3`，Phase 3C 保留了首页巴士卡片的 key 和渲染分支。巴士与铁路分别持有请求及刷新状态。用真实 B2 卡片、Hook 和请求函数运行定向测试时，旧版在请求已收到 abort 后仍渲染 Loading。测试在并行铁路读取的情况下运行，修复后连接卡住、响应体卡住都在 20 秒后显示超时。另验证了正常 ETA、HTTP 失败、网络失败和空预报均结束加载。迟到的响应体不会覆盖超时，下一次正常轮询能恢复 ETA。

本机现存 Simulator 日志和近四小时系统统一日志没有捕获该次人工事件的巴士请求记录。已确认上述代码缺陷以及修复效果。人工验收时 B2 的实际网络阶段仍需在原环境核对。

## 修改与风险

| `scripts/test-bus-route-map.cjs` | 通过真实 B2 卡片验证超时、恢复、迟到响应、成功、失败、空预报和并行铁路读取。 |

| `src/i18n.ts` | 首页铁路状态改用简短的繁中和英文提示。 |
| `scripts/test-mtr-next-train.cjs` | 验证紧凑卡片、可换行状态行、刷新点击区域、加载及预报状态。 |
| 本报告 | 根因、范围与验收交接。 |

共用巴士 HTTP 请求函数是缺陷发生点，因此修复也覆盖使用该函数的巴士目录及站点资料请求。20 秒内的成功响应、解析、现有错误分类和 429 调度沿用原逻辑。遇到原生传输不响应 abort 时，JavaScript 会先结束等待。底层连接实际何时释放仍取决于系统网络层。巴士 ETA Hook、收藏数据、SQLite、铁路方向、路线过滤、同站去重及前后台策略均维持 Phase 3C 实现。

## 卡片前后布局

原卡片把交通类型、线路和站名分成三行，再用独立「下一班列車」工具栏放刷新。每组预报有独立月台行，底部另占一行显示资料时间。现在首行组以站名为主，类型和线路合并成一行，右边放 28 pt 刷新图标和独立 44 × 44 pt 点击区。预报区只留一个分隔线，每组以目的地、方向或月台及到站／开出语义呈现，并保留右侧 ETA。完整时间与资料更新时间可在原详情查看。

加载、空、失败及过期使用短状态行。长站名、预报文字及错误说明可以随系统字体自然换行。可显示的方向或月台上限沿用 Phase 3C。
